# The facts bowline rests on

bowline measures a repository against limits that are Claude Code's, not bowline's. Every number below is also a setting in
`defaults.json`, with its reason beside it, and the doctor prints which it used. When Claude Code changes one, the two
files change together and the changelog says so.

Checked against the Claude Code documentation on **2026-11-14**; the three rows about a hook after a tool call, a
hook's `if` field and what every hook receives were read on **2026-11-21**. Each row says whether the documentation
states it or whether it was observed on a machine.

| The project folder's name | the repository's path with every character other than a letter or a digit replaced by `-` | Observed on Windows (`I:\Tal\Code\other\repo` became `I--Tal-Code-other-repo`); the documentation describes transcripts this way but does not state the rule for memory | sessions.md |

| Compaction while idle | on by default (`idleCompaction`): a conversation that has reached 200,000 tokens and has been quiet for about an hour is summarized before the next message | Documented | settings-reference.md |
| What survives a compaction from disk | the root `CLAUDE.md`, unscoped rules, the memory index and skill bodies (to a cap) are re-injected; nested `CLAUDE.md` files and scoped rules only when their trigger file is read again | Documented | context-window.md |
| A plugin can ship skills, hooks, agents and scripts, but not a `CLAUDE.md` or rules | "A `CLAUDE.md` at the plugin root isn't loaded as context" | Documented | plugins-reference.md |
| A headless session, which autosplit's worker starts | `claude -p` prints the answer and exits; `--permission-mode acceptEdits` accepts file edits in the working folder; `--permission-prompts none` denies anything that would ask a person; `--allowedTools` lists what may run without asking; `--max-budget-usd` caps the spend; `--output-format json` ends with one object carrying `total_cost_usd`, `num_turns`, `session_id`, `is_error` and, on an error, `subtype` and `errors` | Documented; the flags and the result observed with Claude Code 2.1.319, and a session started from inside another session's hook environment | headless.md |
| What a Stop or SessionEnd hook receives on its standard input | JSON with `session_id`, `transcript_path`, `cwd` and `hook_event_name`; a Stop hook also `last_assistant_message`, "the text content of Claude's final response", which the documentation advises over the transcript, since "the transcript file isn't guaranteed to include the final message at Stop time on all versions" | Documented, read 2026-11-21 | hooks.md |
| The session a command runs in | `CLAUDE_CODE_SESSION_ID` is "set automatically to the current session ID in Bash and PowerShell tool subprocesses, hook command subprocesses, and stdio MCP server subprocesses", the same as a hook's `session_id` | Documented, read 2026-11-21 | env-vars.md |
| Edits under `.claude/` by the Edit and Write tools | are sensitive-file edits that need a person's approval even in `acceptEdits` mode and even with an allow rule for the path; with `--permission-prompts none` they are denied, while a script run through an allowed Bash command writes there (which is how `move run` and `move place` write rule files) | Observed with Claude Code 2.1.319; the refusal reads "Claude requested permissions to edit `.claude/rules/probe.md` which is a sensitive file"; not found in the documentation | (observed) |
| What a hook's output reaches | Plain stdout from a SessionStart or UserPromptSubmit hook is added to Claude's context ("Claude Code adds plain-text stdout as context that Claude can see and act on"); plain stdout from a Stop hook reaches neither Claude nor the person; a JSON `systemMessage` from any hook is shown to the person as a warning; a Stop hook's `decision: block` keeps the turn going with its `reason` given to Claude | Documented | hooks.md |
| What a PostToolUse hook can tell Claude | A JSON answer with `hookSpecificOutput.additionalContext` is "added to Claude's context alongside the tool result"; plain stdout from a PostToolUse hook is not among the events whose stdout becomes context, and "Claude never sees stderr from a hook that exits 0". The hook runs after a tool call that succeeded; a failed one is PostToolUseFailure. bowline's checks after `git rebase`, `git pull` and `git push` answer this way | Documented | hooks.md |
| What a PreToolUse hook can tell Claude | A JSON answer with `hookSpecificOutput.additionalContext` and the event's name: "Claude Code wraps the string in a system reminder and inserts it into the conversation at the point where the hook fired", for a PreToolUse hook "next to the tool result". A hook that gives no decision does not approve anything: "Exit code 0 with no output means the hook has no decision to report, so the tool call continues through the normal permission flow. The hook can deny the call, but staying silent doesn't approve it." Plain stdout from a PreToolUse hook is not among the events whose stdout becomes context. bowline's check before an edit answers this way, with no `permissionDecision` | Documented | hooks.md |
| A hook's `if` field | "holds exactly one permission rule. There is no `&&`, `\|\|`, or list syntax for combining rules; to apply multiple conditions, define a separate hook handler for each"; for Bash, each subcommand of a compound command is checked. A matcher may list tools, and "the matcher `Bash\|PowerShell` covers the PowerShell tool as well as Bash". So bowline has one handler per git command and per shell tool | Documented | hooks.md |
| What every hook receives | JSON on standard input with `session_id`, `transcript_path` and `cwd`, whatever the event; a tool event adds `tool_input`, and for a shell tool `tool_input.command` | Documented | hooks.md |
| A file that changed since Claude read it | The Write tool refuses it ("File has been modified since read, either by the user or by a linter. Read it again before attempting to write it."); the Edit tool applies its replacement to the file as it is now and says that the file "had been modified on disk since you last read it". A shell redirect, `Set-Content` or a script notices nothing. So lines another session added to a shared file survive an Edit and are lost only to a whole-file write | Observed with Claude Code in the desktop app on Windows, 2026-11-21: a file read, changed from a shell, then written and edited; not found in the documentation | (observed) |
| Where a worktree's sessions leave a trace | Each worktree of a repository has its own project folder in Claude Code's configuration, named from the worktree's path like any project's, and a session started there writes its transcript there as it works; the memory folder is the main checkout's, shared by all of them. A session started in another folder that works in a worktree by path writes its transcript in the folder it started in, so the worktree's project folder shows nothing of it. bowline reads when the newest transcript was written, and of what it holds only the title line at its end, and takes the worktree's own git folder being written, and a claim, as signs of work too | Observed on Windows, 2026-11-21, with eleven worktrees of one repository, and with one session that worked in a worktree of a repository it was not started in | (observed) |
| The sessions Claude Code lists | `claude agents --json` prints every session on the machine as a JSON array, Claude Desktop's and background ones included, each with `name`, `cwd`, `kind` (`interactive`, `background`), `pid`, `sessionId`, `startedAt` in milliseconds, and `status` (`busy`, `idle`) or, for a background one, `state` (`blocked`); it answered in 0.3 to 1 second, and with an empty `CLAUDE_CONFIG_DIR` it prints `[]`. A session's transcript is `<sessionId>.jsonl` in the project folder of its `cwd`, and Claude Code writes the session's title into it again and again as a line `{"type":"custom-title","customTitle":...}`, so the file's end holds the newest. Claude Desktop starts every session's `claude.exe` with `--project-config-root` naming the main checkout, a session in a worktree too | Observed with Claude Code 2.1.330 and Claude Desktop on Windows, 2026-11-21, with 28 sessions; `claude agents --help` describes `--json` as "for scripts" | (observed) |
| Claude Desktop's record of a Code session | The app keeps one JSON file per Code session, `claude-code-sessions/<account>/<organization>/local_<id>.json` in its own folder (`%APPDATA%\Claude` on Windows), with `sessionId` (`local_<uuid>`, the app's own id), `cliSessionId` and `lastAssistantCliSessionId` (the `sessionId` that `claude agents --json` lists), `title` in full, `isArchived`, `cwd`, `worktreePath` and `lastActivityAt` in milliseconds, among many settings. A reply in the app links a session as `[its title](#local_<uuid>)`, by the app's id, which `claude agents` does not give; its `name` is the title cut at 50 characters. 42 records of about 180 KB each were read in 0.03 seconds. A session of the app whose process has ended stays in the sidebar, and its record stays, until the person archives it; `claude agents --json` does not list it, while `ListAgents` lists it as "Remote Control, offline" | Observed with Claude Desktop 5.11492.5 and Claude Code 2.1.330 on Windows, 2026-11-22, against the app's own list of sessions; not documented | (observed) |
| Claude Code's record of a running process | Each Claude Code process writes `sessions/<pid>.json` in the configuration folder, with `pid`, `sessionId`, `cwd`, `name`, `kind` (`interactive`, `bg`), `status`, `startedAt` and `version`, beside a `<pid>.<hash>.key` file; a record stays after its process ends. Of sixteen Claude Code processes, `claude agents --json` listed every one that was not elevated and none of the ten that ran as administrator: six of those had a record of an interactive session it left out, one was the process of a background session it listed with no process, and three had no record. A Node `process.kill(pid, 0)` answers EPERM for an elevated process and nothing for one that is not, which would explain it if Claude Code tests its processes that way; its code was not read to confirm it | Observed with Claude Code 2.1.316 to 2.1.330 on Windows, 2026-11-22; not documented | (observed) |
| A process that runs as administrator | A program that is not elevated is refused `PROCESS_QUERY_INFORMATION` and `PROCESS_VM_READ` for it (error 5, access denied), so `Win32_Process` gives an empty `CommandLine` and `ExecutablePath`, and `Get-Process` no path and no modules; `PROCESS_QUERY_LIMITED_INFORMATION` is granted, with which `QueryFullProcessImageNameW`, `GetProcessTimes` and the token's `TokenElevation` answer. When Claude Code updates itself while it runs, the running binary is renamed `claude.exe.old.<milliseconds>.<pid>`, and that is the path Windows gives | Observed on Windows 11 with ten elevated `claude.exe` processes, 2026-11-22; the access rules are Windows' own (OpenProcess, process security and access rights) | (observed) |
| A git command in another worktree | `git status` refreshes the index of the worktree it runs in and takes its lock for a moment, so a look into another session's worktree can make that session's own git command fail on `index.lock`; `git --no-optional-locks` reads without it. A person's `log.showSignature` adds a line of words before every commit that `git log` prints, and checks each signature; `--no-show-signature` turns both off for one command | Documented in git's own manual (`--no-optional-locks`, `log.showSignature`); the failure reported by a session on 2026-11-21 | git, git-log |
| Which shell runs a hook's `command` | `sh -c` on macOS and Linux; Git Bash on Windows, or PowerShell when Git Bash is not found (a hook may name its shell with a `shell` field; `CLAUDE_CODE_GIT_BASH_PATH` names the bash to use). In PowerShell a quoted script path followed by arguments is a parse error, so bowline's shell-form hooks need Git Bash on Windows; a headless session started from an environment that hides Git Bash fell back to PowerShell and its hooks failed | Documented; the fallback observed on Windows with Claude Code 2.1.319 | hooks.md |

## What follows from these facts

- **A `CLAUDE.md` that grows is read less, not more.** Past 200 lines adherence drops; past the cutoff the rest is not
  read at all unless Claude decides to look. A repository whose conventions live in one growing file is applying a
  shrinking share of them, and nothing tells it so. bowline's doctor tells it so, naming the line and the section where
  the cut falls.
- **The home of a piece of knowledge follows how Claude Code loads it.** A rule that concerns one part of the code
  belongs in a scoped rules file, so it loads only then and loads whole. A procedure belongs in a skill, so its body
  costs nothing until it is used. A decision or a history belongs in a document, read when someone asks why. The root
  `CLAUDE.md` stays short because it is the one file every session pays for.
- **Memory is a working notebook, not a record.** It is personal by design, loads only its index at start, and is lost
  with the machine. What a project needs every contributor to know is promoted into the repository; what is personal
  stays, backed up to a private remote by a hook, and the index is kept short so the newest notes are not the ones
  that fall off.
- **A summary needs instructions.** Without a "Compact Instructions" section, a long session's state is kept or lost
  at the summary's discretion.
